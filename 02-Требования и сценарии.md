# Требования и сценарии

## 2.1 Роли и права доступа

| Роль                  | Ответственность                           |
| --------------------- | ----------------------------------------- |
| Инициатор             | Создание и подача заявки                  |
| Эксперт               | Проверка заявки и документов              |
| Финансовый специалист | Проверка бюджета и финансовых параметров  |
| Согласующий           | Принятие решения по заявке                |
| Заместитель директора | Утверждение заявки                        |
| Администратор         | Управление пользователями и справочниками |

---

## 2.2. User Story

**US-01. Подача заявки**

> Как инициатор, я хочу создать и отправить заявку на финансирование проекта, чтобы получить финансирование.

**US-02. Проверка заявки**

> Как эксперт, я хочу проверить заявку и документы, чтобы определить их соответствие требованиям и принять решение.

**US-03. Финансовая экспертиза**

> Как финансовый специалист, я хочу проверить бюджет и параметры финансирования, чтобы определить возможность финансирования проекта, составить обоснование или опровержение и принять решение.

**US-04. Принятие решения**

> Как согласующий, я хочу рассмотреть, затем согласовать, отклонить или вернуть заявку на доработку.

**US-05. Утверждение заявки**

> Как заместитель директора, я хочу рассмотреть, затем утвердить заявку, вернуть ее согласующему или отклонить. 

---

## 2.3. Use Case

### UC-01. Подача заявки

**Актор:** Инициатор

**Предусловие:** пользователь авторизован.

**Основной сценарий:**

1. Инициатор создаёт заявку.
2. Заполняет данные проекта и финансирования.
3. Прикладывает обязательные документы.
4. Система выполняет валидацию.
5. Инициатор назначает согласующее лицо из отфильтрованного списка
6. Инициатор отправляет заявку.
7. Система проверяет комплектность.
8. Система блокирует редактирование заявки
9. Заявка переводится на следующий этап.

**Постусловие:** Заявка находится в статусе 'На рассмотрении'. Редактирование/удаление заявки запрещено

**Альтернативные сценарии:**

* данные не прошли валидацию → система отображает ошибки;
* отсутствуют обязательные документы → заявка не отправляется;
* заявка возвращена на доработку → инициатор редактирует и повторно отправляет её.

### UC-02. Согласование заявки

**Актор:** Согласующий

**Предусловие:** заявка пришла на согласование

**Основной сценарий:**

1. Система оповещает согласующее лицо о поступлении новой заявки
2. Согласующее лицо принимает заявку в работу
3. Рассматривает заявку
4. Принимает решение 'Согласовать'
5. Отправляет заявку заместителю директора

**Постусловие:** Заявка находится в статусе 'На утверждении'

**Альтернативные сценарии:**

* согласующий вернул заявку на доработку → инициатор получает заявку на доработку, редактирование заявки доступно
* согласующий отклонил заявку → инициатор получает оповещение об отклонении

### UC-03. Утверждение

**Актор:** Заместитель директора

**Предусловие:** заявка была согласована

1.  Система оповещает заместителя директора о поступлении новой заявки
2.  Заместитель директора принимает заявку в работу
3.  Изучает историю рассмотрения заявки экспертами и согласующим лицом
4.  Принимает решение 'Утвердить'
5.  Заявка переходит в статус 'Утверждена'
6.  Данные заявки отправляются во внешнюю систему

**Постусловие:** Заявка находится в статусе 'Утверждена'. Данные заявки переданы во внешнюю систему

**Альтернативные сценарии:**

* заместитель директора отклонил заявку → все участники процесса получают уведомление об отклонении заявки
* заместитель директора вернул заявку на доработку → заявка возвращается согласующему лицу, а не инициатору

## 2.4. Функциональные требования

| ID    | Требование                                                                           |
| ----- | ------------------------------------------------------------------------------------ |
| FR-01 | Система должна позволять создавать и редактировать заявку до её подачи.              |
| FR-02 | Система должна проверять обязательные поля и документы перед подачей.                |
| FR-03 | Система должна позволять выбирать ответственных лиц из доступных пользователей.      |
| FR-04 | Система должна блокировать редактирование и удаление заявки во время рассмотрения.   |
| FR-05 | Система должна управлять переходами заявки между этапами процесса.                   |
| FR-06 | Система должна предоставлять участникам процесса операции в соответствии с их ролью. |
| FR-07 | Система должна фиксировать результаты проверки, согласования и принятого решения.    |
| FR-08 | Система должна сохранять историю изменения статусов заявки.                          |
| FR-09 | Система должна передавать данные утверждённой заявки во внешнюю финансовую систему.  |

---

## 2.5. Нефункциональные требования

| ID        | Категория           | Требование                                                                                             |
| --------- | ------------------- | ------------------------------------------------------------------------------------------------------ |
| NFR‑01    |	Безопасность      	| Доступ к данным и операциям определяется ролью пользователя.                                           |
| NFR‑02	  | Надёжность	        | Сбой внешней системы не должен приводить к потере данных заявки.                                       |
| NFR‑03	  | Аудит	              | Критичные операции и изменения заявки должны фиксироваться в журнале аудита.                           |
| NFR‑04  	| Производительность  |	Основные пользовательские операции должны выполняться не более чем за 2 секунды при штатной нагрузке.  |
| NFR‑05  	| Интеграции          | Повторная обработка одного сообщения не должна приводить к дублированию финансовой операции.           |
