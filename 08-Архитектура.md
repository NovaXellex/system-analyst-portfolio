# 08. Архитектура

## 8.1. Архитектурный подход и ключевые решения

Система построена на следующих принципах:

- REST API как основной стиль взаимодействия;
- API Gateway в качестве единой точки входа;
- горизонтальное масштабирование API-приложений (stateless);
- PostgreSQL в качестве основного хранилища данных;
- RabbitMQ для асинхронных операций;
- отдельные воркеры для интеграций и уведомлений;
- внешние системы: Identity Provider, File Storage, Financial System.

Основная бизнес-логика остаётся в одном API-приложении  
Асинхронные и потенциально долгие операции вынесены в отдельные воркеры, чтобы не блокировать пользовательские запросы.

Ключевые технологические решения:

- RabbitMQ выбран вместо Kafka;
- Redis и read-replica PostgreSQL на текущем этапе не применяются;
- архитектура позволяет при росте нагрузки масштабировать API и воркеры независимо.

## 8.2. C4 — System Context

На уровне System Context система рассматривается как «чёрный ящик».

![C4 System Context](C4-Context.jpg)

**Участники:**

- **Пользователь** — работает с заявками;
- **Администратор** — управляет системой;
- **Identity Provider** — аутентификация и авторизация;
- **File Storage** — хранение файлов заявок;
- **Financial System** — получение данных утверждённых заявок.

## 8.3. C4 — Container Diagram

На уровне System Container диаграмма показывает общую форму архитектуры, распределение функций и обязанностей.

![C4 Container Diagram](C4-Container.jpg)

Система раскрывается на следующие основные части:

| Контейнер              | Технология          | Назначение |
|------------------------|---------------------|----------|
| Frontend               | HTML                | Пользовательский интерфейс |
| API Gateway            | NGINX               | Единая точка входа, маршрутизация, проверка токенов |
| Webapi                 | .NET Core (C#)   | Основная бизнес-логика, stateless, горизонтальное масштабирование |
| PostgreSQL             | PostgreSQL          | Основная база данных |
| RabbitMQ               | RabbitMQ            | Очередь асинхронных событий |
| Integration Worker     | .NET Worker         | Отправка данных в Financial System |
| Notification Worker    | .NET Worker         | Отправка уведомлений участникам процесса |

### Аутентификация и авторизация

Identity Provider отвечает за аутентификацию пользователя и выдачу `access token`.

API Gateway выполняет первичную проверку валидности токена и маршрутизацию запроса в Backend API.

Backend API определяет пользователя по данным токена и выполняет авторизацию бизнес-операции с учётом его роли и текущего этапа заявки.

## 8.4. Асинхронное взаимодействие и RabbitMQ

Указанные операции не должны выполняться синхронно в рамках пользовательского HTTP-запроса:

1. Передача утверждённой заявки во внешнюю Financial System (может быть долгой и ненадёжной).
2. Отправка уведомлений участникам процесса при смене статуса заявки.

### Сценарии использования RabbitMQ

**1. Интеграция с Financial System**
- После финального утверждения заявки API публикует событие.
- Integration Worker забирает сообщение, получает токен, отправляет данные.
- При временных ошибках сообщение может быть обработано повторно.
- После исчерпания попыток сообщение попадает в Dead Letter Queue (DLQ).

**2. Уведомления**
- При смене статуса заявки (поступление на согласование, утверждение, отклонение, возврат) публикуется событие.
- Notification Worker отправляет уведомления соответствующим участникам процесса.

### Почему RabbitMQ, а не Kafka

Kafka имеет смысл при большом потоке событий, необходимости хранить историю событий долгое время или построении event-sourcing.  
На текущем этапе RabbitMQ является более простым и достаточным решением.

Защита от повторного создания финансовой операции (идемпотентность) описана в разделе [07. Интеграции](./07-Интеграции.md).

## 8.5. Масштабирование и отказоустойчивость

| Компонент               | Решение                                    | Комментарий |
|-------------------------|--------------------------------------------|-----------|
| API                     | 2+ экземпляра                              | Stateless, легко масштабируется |
| API Gateway             | Единая точка входа                         | Маршрутизация и проверка токенов |
| RabbitMQ                | Один брокер (при необходимости — кластер)  | Асинхронная обработка |
| Integration Worker      | Несколько экземпляров                      | Масштабируется независимо |
| Notification Worker     | Несколько экземпляров                      | Масштабируется независимо |
| PostgreSQL              | Один экземпляр                             | Для текущего масштаба достаточно |
| Read Replica PostgreSQL | Не используется                            | Можно добавить при росте чтения, потребности в аналитике|
| Redis                   | Не используется                            | Нет необходимости в кэше |

**Пояснение**

Для текущего масштаба системы репликация PostgreSQL и отдельный кэш не требуются.  
При увеличении нагрузки в первую очередь масштабируются API и воркеры.  
При значительном росте нагрузки на чтение может быть добавлена read-replica PostgreSQL и Redis.

### Transactional Outbox

При необходимости гарантированной публикации событий может использоваться Transactional Outbox.

В рамках одной транзакции БД сохраняются изменения бизнес-сущности и запись о событии, которое необходимо опубликовать.

Отдельный процесс публикует записи Outbox в RabbitMQ.

В текущей демонстрационной архитектуре Outbox не выделен в отдельный контейнер и рассматривается как возможное развитие решения.

## 8.6. Итоговые архитектурные принципы

* Пользовательские операции, не требующие длительной обработки, выполняются через Backend API
* Операции, зависящие от внешних систем или требующие фоновой обработки, могут выполняться через брокер сообщений и фоновые обработчики
* API не выполняет длительные интеграционные операции в рамках пользовательского HTTP-запроса
* Backend API и фоновые воркеры являются stateless и могут масштабироваться независимо
* Повторная обработка интеграционных сообщений не должна приводить к дублированию операции
* При временной недоступности внешней системы сообщение может быть обработано повторно
* После исчерпания количества попыток сообщение помещается в Dead Letter Queue

Архитектура позволяет развивать систему эволюционно: масштабировать API и воркеры независимо, добавлять новые асинхронные сценарии и при необходимости применять дополнительные механизмы надёжной доставки сообщений.
